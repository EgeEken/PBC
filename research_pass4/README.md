# Reproduce Pass 4

Run from the repository root in the recorded local Python environment. Do not rerun commands over preserved results for an independent experiment; use a separate output directory. No command below changes production, prior research, models, datasets or databases. Primary CPU jobs run sequentially, on one CPU with numerical threads set to one. JSON/JSONL records are authoritative; CSV contains scalar columns.

1. `python research_pass4/runner.py initial` captures the checkout/runtime/model/input environment and verifies the previous manifests. It refuses to overwrite the initial snapshot.
2. `python research_pass4/runtime.py exactness`; `python research_pass4/runner.py runtime_exactness`; `python research_pass4/runtime.py edges`. Verify byte/pixel/patch/MSE/bpp identity, intermediate proposal ordering and RNG states before timing.
3. `python research_pass4/runtime.py screen`; `python research_pass4/runner.py runtime_screen`; `python research_pass4/analysis.py runtime_screen`. Qualified full plan/run: runtime.py full, runner.py runtime_full, analysis.py runtime_full. All four modes are interleaved within a persistent worker, three warmed repetitions. Cache creation, search installation and cleanup are charged inside compress wall time.
4. `python research_pass4/hf_probe.py` performs read-only public HTTP GETs and saves health/schema/status/reported-revision observations. It does not start jobs or upload anything. The environment must allow networking; sandbox DNS failures are retained separately. Source checks fetch only nine text files at the reported immutable revision. No model/dataset upload or arbitrary remote execution is involved.
5. `python research_pass4/matched_rate.py diagnostic`; `python research_pass4/matched_rate.py controls`; `python research_pass4/analysis.py matched`. The first command reconstructs prior brackets. The second makes at most six fresh ordinary-codec settings per image, using bitrate alone to choose the next budget/q, with frozen allocator targets. These exploratory calls warm once per q value and do not support precise speed claims. All files are complete fresh encodes, not extracted prefixes.
6. `python research_pass4/runner.py matched_confirmation` uses the generated frozen plan: each nearest fresh control and the unchanged allocator, all 25 images, three interleaved warmed repetitions. All unique settings receive complete warmups. Timing against these smaller-budget controls includes actual extra search work and is separate from equal-budget allocator overhead.
7. `python research_pass4/regressions.py` instruments the frozen allocator on the four named regressions; outputs must equal Pass 3. It records every considered representation and ordinary stop, with no extra search or model evaluations. Local SSE is a working-channel diagnostic, not a replacement RGB metric.
8. `python research_pass4/efficiency.py profile`; `python research_pass4/runner.py efficiency_profile`; `python research_pass4/efficiency.py efficiency_profile`. Review function self/cumulative costs, calls and full encoder walls before choosing the two mechanisms. These instrumented calls are separate from primary latency.
9. After reviewing the cost decision: efficiency.py screen, runner.py efficiency_screen, efficiency.py efficiency_screen. Screen ordinary/frozen/projection/before-SSE/composition, then promote only a qualified exact composite. Full confirmation uses ordinary/frozen/composite on all 25 images, three repeats. Optional fast comparison uses all runtime changes identically in ordinary/frozen/optimized cases; it does not attribute generic runtime gains to the allocator.
10. `python research_pass4/integration_patch.py`; `git apply --check research_pass4/proposed_hf_benchmark.patch`; `python research_pass4/integration_checks.py`. These create and validate isolated files; the patch remains unapplied. A LOCAL_PACKAGING_SMOKE call to hf_runtime_job.py verifies the portable package after all primary CPU jobs, without using HTTP or running on HF.
11. `python research_pass4/plot.py`; `python research_pass4/report.py`; `python research_pass4/final_checks.py`. Reports use conclusions.json recorded after reviewing the raw data. The final check verifies prior artifacts, production/model/input hashes, determinism, stored streams, exact runtime/cache candidates, API proposal applicability, all deliverables and the changed-file inventory.

The benchmark reuses Pass 2's isolated worker/parser/metrics/summary utilities read-only, plus Pass 3's exact frozen selector/grid/search implementations. support.py redirects only in-memory output paths to this directory. The worker imports release/current sources in separate processes where required; current default RNG is retained in all new candidates. Source/module/model/input identifiers and expanded configs are stored per experiment, with before/after snapshots and three-repeat variability.

Matched comparisons retain direct measured rates and signed gaps separately from interpolated estimates. A 5% rate tolerance is not exact equality. The strongest actual close control minimizes MSE among all measured controls within that tolerance, rather than choosing an especially poor ordinary setting. Measured dominance across all rates is also checked. Prior and densified interpolations remain separate; the conservative estimate takes the lower interpolated baseline MSE of the two so adding points cannot manufacture a gain by weakening the old chord. No extrapolation, BD-rate or continuous-curve dominance claim is made.
